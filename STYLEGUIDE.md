# Стайлгайд вики

Версия 0.1 · 2026-11-11. Обязателен для всех страниц.

## 1. Язык и терминология

- Текст — русский; код, имена задач, модулей, файлов, путей и команд — английский.
- При первом упоминании термина в тексте: русский вариант + English в скобках, например «идемпотентность (idempotency)». Далее — один вариант.
- Названия модулей — только FQCN: `ansible.builtin.copy`, `ansible.posix.sysctl`, `community.vmware.vmware_guest`.
- Не переводить имена продуктов и компонентов: AWX, AAP, Execution Environment, handler, playbook, inventory.
- Единые написания: «control node», «managed node», «playbook», «role», «collection», «ansible-core», «AWX», «AAP», «vCenter», «ESXi», «Kubernetes».
- Не использовать «Tower» для актуальных версий; при исторической ссылке — «Ansible Tower (ныне Automation Controller)».

## 2. Структура страницы

Каждый файл начинается с frontmatter:

```yaml
---
title: "..."
slug: "..."
part: "start | fundamentals | secure-dev | admin | security | quality | ops"
audience: ["sysadmin", "secops", "soc", "architect", "manager"]
level: "basic | intermediate | advanced"
applies_to:
  ansible_core: ">=2.17"
  os: ["rhel9", "ubuntu24.04", "debian12"]
collections: ["ansible.posix", "community.general"]
security_impact: "low | medium | high | critical"
last_reviewed: "YYYY-MM-DD"
owners: ["tbd"]
---
```

Обязательные разделы:

1. Зачем это нужно.
2. Ключевые понятия (таблица).
3. Схема (Mermaid, если уместно).
4. Пошаговая реализация.
5. Примеры кода (полные).
6. Проверка результата.
7. Безопасность и blast radius.
8. Комплаенс-маппинг (если применимо).
9. Типичные ошибки и troubleshooting.
10. Чек-лист.
11. Источники.
12. Связанные страницы.

## 3. Заголовки и объём

- Один `H1` на страницу, совпадает по смыслу с `title`.
- `H2` — обязательные разделы; `H3` — подразделы, не глубже.
- Заголовки без нумерации, кроме пошаговых инструкций.
- Объём: 800–2500 слов; глоссарий и крупные хабы — до 3500.
- Абзацы короткие, 2–5 предложений. Списки — для перечислений, таблицы — для сравнений.

## 4. Код

- Полный запускаемый пример: `hosts`, `become` только где нужно, `vars`, задачи с `name`.
- FQCN обязателен. Для каждого модуля указывать коллекцию.
- Идемпотентность: `changed_when`/`failed_when` по необходимости, `creates`, handlers для сервисов.
- Конфиги — через `template`/`copy` с `validate` (`sshd -t -f %s`, `visudo -cf %s`, `nginx -t`).
- `shell`/`command` — только при отсутствии модуля, с `argv`, `creates` и пояснением.
- Секреты — `!vault`, внешние lookup или credentials платформы; в примерах заглушки.
- `no_log: true` для задач с секретами; указывать ограничения.
- Рискованные изменения: `--check --diff` → `serial: 1` → полная раскатка; описывать откат.
- Не показывать в продакшн-примерах `host_key_checking=False`, `validate_certs=False`, `chmod 777`, `ignore_errors` без причины.
- Коллекции — в `requirements.yml` с точными версиями.
- Комментарии в коде — короткие, на английском, только там, где неочевиден смысл.

## 5. Безопасность контента

- Только defensive-практики. Без эксплуатации уязвимостей, C2 и обхода защиты.
- Для каждого изменения указывать blast radius и способ отката.
- Least privilege: минимальный `become`, отдельные сервисные учётки, ограниченные права.
- Предупреждать о риске самоблокировки при изменении firewall, SSH, sudo и сети.
- Отмечать действия, требующие ручного апрува.
- CVE, цифры и цитаты — только с источником; иначе переформулировать или помечать TODO.

## 6. Ссылки и навигация

- Относительные ссылки от `docs/`: `../security/35-linux-hardening.md`.
- В конце страницы — 4–8 связанных страниц.
- Не ссылаться на несуществующие файлы в опубликованных страницах; для запланированных — plain text до публикации.
- Якоря — kebab-case, на английском.
- Внешние ссылки — на официальную документацию; без выдуманных URL.

## 7. Диаграммы и таблицы

- Mermaid: `flowchart` для архитектуры и потоков, `sequenceDiagram` для взаимодействий, `C4`-подобные схемы не обязательны.
- Подпись под каждой диаграммой: что важно на схеме.
- Таблицы: шапка с осмысленными названиями, без пустых ячеек, единицы измерения.
- Сравнения — таблицей; пошаговые действия — нумерованным списком.

## 8. Версии и источники

- Baseline: ansible-core 2.17+; control node Python 3.10–3.12; managed nodes Python 3.7–3.12.
- Для RHEL 8 учитывать отсутствие поддержки Python 3.6 начиная с 2.17; использовать python39.
- Указывать «начиная с версии X», если поведение менялось.
- Источники: docs.ansible.com, galaxy.ansible.com, dev-sec, ansible-lockdown, complianceascode.io, NIST, MITRE ATT&CK, VMware docs, Red Hat AAP, kubernetes.core.
- В конце страницы — раздел «Источники» с проверенными ссылками.

## 9. Оформление предупреждений

- `!!! warning "Риск"` — для изменений с высокой ценой ошибки.
- `!!! note "Контекст"` — для важных пояснений.
- `!!! tip "Практика"` — для рекомендаций.
- `!!! danger "Только для лаборатории"` — для небезопасных в продакшене приёмов.
- Не злоупотреблять: не больше 2–3 врезок на страницу.
