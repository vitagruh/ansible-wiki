# Глоссарий

Единая терминология вики. Правило: при первом упоминании в тексте — русский термин и English в скобках, далее — один вариант. Код, имена модулей и задач — на английском. Термины сгруппированы по темам; порядок внутри групп — от базовых понятий к прикладным.

**Категории:** [Основы Ansible](#basics) · [Переменные и шаблоны](#variables) · [Запуск и тестирование](#run) · [Платформы](#platforms) · [Безопасность](#security) · [Инфраструктура и эксплуатация](#infra)

## 1. Основы Ansible {#basics}

| Термин | Определение |
|---|---|
| **Ansible** | Платформа автоматизации конфигурации, развёртывания и оркестрации. Описывает желаемое состояние в YAML и применяет его к узлам по сети без установки агента. |
| **ansible-core** | Минимальный движок Ansible: CLI (`ansible`, `ansible-playbook`, `ansible-galaxy`), встроенные модули и плагины. Остальной функционал поставляется коллекциями. |
| **Control node (управляющий узел)** | Машина, с которой запускаются playbook и ad-hoc команды. Для ansible-core это POSIX-система; Windows как control node не поддерживается. |
| **Managed node (управляемый узел)** | Целевой хост, к которому применяются задачи. Для Linux требуется Python (3.7–3.12 для ansible-core 2.17+), для сетевых устройств — соответствующий connection plugin. |
| **Agentless (безагентный)** | Модель без постоянного агента на целевых узлах: SSH для Linux, WinRM/PSRP для Windows, `network_cli` для сетевого оборудования. |
| **Inventory (инвентарь)** | Перечень управляемых узлов и их группировка. Бывает статическим (INI/YAML) или динамическим (inventory plugin). |
| **Playbook** | YAML-файл со сценарием автоматизации, состоящий из одного или нескольких play. |
| **Play** | Блок playbook, связывающий группу хостов с набором задач, переменных и параметров выполнения. |
| **Task (задача)** | Атомарный шаг play, вызывающий один модуль с параметрами. Должна быть идемпотентной и иметь осмысленный `name`. |
| **Role (роль)** | Переиспользуемый набор задач, handlers, шаблонов, файлов, значений по умолчанию и метаданных с фиксированной структурой каталогов. |
| **Collection (коллекция)** | Формат упаковки модулей, плагинов, ролей и документации: пространство имён и имя, например `community.vmware`. |
| **Module (модуль)** | Единица работы, реализующая операцию над системой: пакет, файл, сервис, API. Большинство модулей идемпотентны и поддерживают check mode. |
| **FQCN** | Fully qualified collection name — полное имя модуля или плагина вида `namespace.collection.module`. Обязательная практика, устраняющая неоднозначность. |
| **Idempotency (идемпотентность)** | Свойство, при котором повторный запуск не меняет систему, если она уже в нужном состоянии. Повторный прогон должен давать `changed=0`. |
| **Declarative approach (декларативный подход)** | Описание целевого состояния вместо последовательности команд. Модуль сам определяет действия для сходимости. |

## 2. Переменные, шаблоны и логика {#variables}

| Термин | Определение |
|---|---|
| **Variable precedence (приоритет переменных)** | Фиксированная иерархия источников переменных (около 22 уровней): от role defaults до `-e`. Определяет, какое значение победит. |
| **Facts (факты)** | Автоматически собранные сведения об узле: ОС, сеть, железо. Собираются через `gather_facts` или модуль `setup`. |
| **Magic variables (магические переменные)** | Встроенные переменные Ansible, доступные без объявления: `inventory_hostname`, `group_names`, `hostvars`, `play_hosts` и другие. |
| **Jinja2** | Шаблонизатор, используемый в переменных, условиях и шаблонах файлов. Поддерживает фильтры, тесты и выражения. |
| **Template (`ansible.builtin.template`)** | Модуль, который рендерит Jinja2-шаблон в файл на целевом узле. Для конфигов обязателен параметр `validate`. |
| **Lookup plugin** | Плагин, получающий данные на control node во время выполнения: файл, переменную окружения, секрет из хранилища. Результат может попасть в логи — учитывайте риски. |
| **Handler** | Задача, запускаемая по `notify` только при изменении и обычно один раз в конце play. Используется для перезапуска сервисов. |
| **Block / rescue / always** | Конструкция группировки задач с обработкой ошибок и гарантированным выполнением финальных действий. Снижает риск частично применённой конфигурации. |

## 3. Запуск, масштаб и тестирование {#run}

| Термин | Определение |
|---|---|
| **Ad-hoc command** | Одноразовый запуск модуля через `ansible` без playbook. Удобен для диагностики, но не заменяет версионируемую автоматизацию. |
| **Forks** | Число параллельных процессов Ansible (по умолчанию 5). Влияет на скорость и нагрузку на control node и сеть. |
| **Serial** | Размер батча хостов для поэтапной раскатки, например `serial: 1` или по филиалам. Ограничивает blast radius. |
| **Canary (канареечная раскатка)** | Применение изменения сначала к одному или нескольким тестовым хостам с проверкой результата, и только затем — к остальным. |
| **Strategy** | Порядок выполнения задач: `linear` (по умолчанию), `free`, `host_pinned`. Влияет на предсказуемость и скорость. |
| **Check mode** | Режим сухого прогона (`--check`), показывающий изменения без применения. Не все модули поддерживают его корректно. |
| **Diff mode** | Режим `--diff`, показывающий различия файлов и конфигураций. Применяется вместе с check mode для ревью изменений. |
| **Tags (теги)** | Метки задач и ролей для выборочного запуска (`--tags`, `--skip-tags`). Требуют дисциплины именования. |
| **delegate_to** | Выполнение задачи на другом хосте, например на bastion или API-узле, от имени исходного хоста. |
| **run_once** | Выполнение задачи только на одном хосте из группы. Часто сочетается с `delegate_to`. |
| **ansible-pull** | Режим, при котором целевой узел сам забирает репозиторий и применяет playbook локально. Применяется для филиалов и изолированных сред. |
| **Fact caching** | Кэширование фактов между запусками (jsonfile, redis и другие) для ускорения и работы при недоступности узлов. |
| **requirements.yml** | Файл зависимостей с точными версиями ролей и коллекций. Обязателен для воспроизводимости. |
| **Execution Environment (EE)** | Контейнерный образ с ansible-core, коллекциями и зависимостями Python. Собирается `ansible-builder`, запускается `ansible-navigator` или платформой. |
| **Molecule** | Фреймворк тестирования ролей и сценариев в контейнерах, ВМ или облаке. Проверяет сходимость, идемпотентность и поведение. |
| **ansible-lint** | Статический анализатор playbook и ролей. Production-профиль обязателен в CI. |
| **yamllint** | Линтер YAML-синтаксиса и стиля. Дополняет ansible-lint. |
| **testinfra** | Библиотека тестов инфраструктуры на pytest. Используется как verifier в Molecule или отдельно. |

## 4. Платформы {#platforms}

| Термин | Определение |
|---|---|
| **AWX** | Open-source веб-платформа и API для запуска Ansible, upstream Automation Controller: проекты, инвентари, credentials, шаблоны, расписания, RBAC, аудит. |
| **AAP (Ansible Automation Platform)** | Коммерческий продукт Red Hat: Automation Controller, Automation Hub, Event-Driven Ansible, automation mesh, поддержка и сертифицированный контент. |
| **Automation Controller** | Компонент AAP (преемник Ansible Tower), управляющий запусками, доступом и аудитом. |
| **Automation Hub** | Приватный репозиторий коллекций и Execution Environments в AAP. Позволяет зеркалировать и распространять проверенный контент. |
| **EDA (Event-Driven Ansible)** | Компонент автоматизации по событиям: rulebook реагирует на события SIEM или мониторинга и запускает действия. |
| **ansible-rulebook** | CLI-рантайм EDA-правил. Позволяет запускать event-driven сценарии без AAP. |
| **Semaphore** | Лёгкая open-source веб-платформа для Ansible с шаблонами, расписаниями и RBAC. Альтернатива AWX при меньших требованиях. |
| **Job template** | Сохранённая конфигурация запуска в AWX/AAP: playbook, inventory, credentials, переменные. |
| **Workflow** | Цепочка job templates с условиями, апрувами и последовательным или параллельным выполнением. |
| **RBAC** | Ролевая модель доступа к объектам платформы: проектам, инвентарям, credentials, шаблонам. |

## 5. Безопасность {#security}

| Термин | Определение |
|---|---|
| **ansible-vault** | Встроенное шифрование файлов и строк Ansible. Пароль хранится отдельно и не коммитится в репозиторий. |
| **Vault password file** | Файл с паролем для `ansible-vault`. Требует строгих прав и защиты; не путать с HashiCorp Vault. |
| **no_log** | Параметр задачи, запрещающий вывод чувствительных данных. Не защищает от всех каналов утечки, включая отладочные сообщения и некоторые callback-плагины. |
| **Secrets manager** | Внешнее хранилище секретов: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, SOPS. Предпочтительнее статических vault-файлов. |
| **Least privilege** | Принцип минимально необходимых прав для пользователей, сервисных учёток, `become` и платформенных ролей. |
| **become** | Механизм повышения привилегий (sudo, su, pbrun, runas). Должен применяться точечно, а не глобально. |
| **Hardening (харденинг)** | Снижение поверхности атаки и приведение системы к защитному baseline. |
| **CIS Benchmark** | Согласованный набор рекомендаций по безопасной настройке с уровнями L1/L2. Применяется для Linux и VMware ESXi. |
| **STIG** | Security Technical Implementation Guide DISA с категориями CAT I–III. Применяется в регулируемых средах. |
| **OpenSCAP** | Инструмент проверки и генерации отчётов по SCAP-профилям (CIS/STIG). Может выполнять ремедиацию, но в Ansible-процессе обычно используется для верификации. |
| **Compliance evidence (доказательства соответствия)** | Артефакты, подтверждающие внедрение контроля: отчёты, логи, результаты проверок. |
| **Blast radius (радиус поражения)** | Масштаб последствий изменения при сбое. Ограничивается `serial`, канареечными хостами, проверками и откатом. |
| **Supply chain (цепочка поставок)** | Доверие к коллекциям, образам Execution Environments и зависимостям. Требует пиннинга, подписи и приватного хаба. |
| **SBOM** | Перечень компонентов и зависимостей артефакта. Используется для анализа уязвимостей и происхождения. |
| **Artifact signing (подпись артефактов)** | Криптографическая подпись коллекций, Execution Environments и бандлов (GPG, cosign/sigstore) для проверки целостности. |
| **Zero trust** | Модель «не доверять по умолчанию»: явная проверка, минимальные права, сегментация, постоянный контроль. |
| **JIT access (just-in-time)** | Временный доступ с ограниченным сроком и автоматическим отзывом. |
| **Break-glass** | Регламентированный аварийный доступ на случай отказа штатных механизмов. Действия логируются и разбираются. |
| **Chain of custody** | Документированная цепочка обращения с доказательствами при инциденте, подтверждающая их целостность. |

## 6. Инфраструктура, сеть и эксплуатация {#infra}

| Термин | Определение |
|---|---|
| **ESXi** | Гипервизор VMware. Не содержит Python, поэтому управляется через vSphere API, а не модулями `ansible.builtin` по SSH. |
| **vCenter** | Центральная платформа управления ESXi и виртуальными машинами. Даёт API для шаблонов, клонирования, кластеров и политик. |
| **community.vmware** | Коллекция модулей Ansible для vSphere API: виртуальные машины, хосты, кластеры, снапшоты, теги. |
| **Snapshot (снапшот)** | Точка восстановления состояния виртуальной машины на момент времени. Не заменяет резервное копирование. |
| **VM template (шаблон ВМ)** | Эталонный образ для клонирования. Для полноценного жизненного цикла требуется vCenter. |
| **Datastore** | Хранилище виртуальных машин (VMFS, NFS, vSAN). Объект управления и контроля ёмкости. |
| **vDS (vSphere Distributed Switch)** | Распределённый виртуальный коммутатор с централизованной сетевой политикой. |
| **Lockdown mode** | Режим ESXi, ограничивающий прямой доступ и оставляющий управление через vCenter. |
| **WAN** | Глобальная сеть между площадками. Для Ansible важны задержка, потери и стабильность канала. |
| **SD-WAN** | Программно-управляемая WAN. Может влиять на маршрутизацию управления и требования к сегментации. |
| **Bastion / jump host** | Контролируемая точка входа в сегмент. Используется как `ProxyJump` или `delegate_to` для управления. |
| **Air-gapped** | Изолированная среда без прямого доступа в интернет. Требует офлайн-зеркал, подписанных бандлов и регламента переноса. |
| **SIEM** | Система сбора и корреляции событий безопасности. Источник событий для EDA и приёмник логов Ansible. |
| **EDR** | Средство обнаружения и реагирования на конечных устройствах. Разворачивается и проверяется через Ansible. |
| **SOC** | Центр мониторинга и реагирования на инциденты. Потребитель автоматизации EDA и отчётов. |
| **CVE** | Идентификатор публично известной уязвимости. |
| **CVSS** | Система оценки критичности уязвимости. Используется для приоритизации патчей. |
| **Drift (дрейф конфигурации)** | Отклонение фактического состояния от описанного в автоматизации. Выявляется check mode, сканами и периодическими прогонами. |
| **Runbook** | Пошаговая операционная инструкция для типовой задачи или инцидента. |
| **GitOps** | Подход, при котором Git является источником истины, а изменения применяются автоматизированным пайплайном. |
| **IaC (Infrastructure as Code)** | Управление инфраструктурой через версионируемые описания и автоматизированные пайплайны. |
