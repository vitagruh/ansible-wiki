# Чек-листы

Чек-лист — это минимальный набор проверок, который отделяет управляемое изменение от рискованного эксперимента. Семь списков ниже покрывают жизненный цикл автоматизации в филиальной сети: от внедрения и харденинга до инцидента и обновления в изолированном сегменте.

## Зачем это нужно

В распределённой сети на 200–1000 хостов цена пропущенного шага высока: забытый `--check`, отсутствие второй SSH-сессии или непроверенный снапшот приводят к отказу филиала. Чек-лист фиксирует порядок действий и доказательства, которые можно предъявить аудитору. Он не заменяет экспертизу, но убирает вариативность: два инженера выполняют изменение одинаково.

Правила использования:

1. Чек-лист открывается до начала работ и закрывается после проверки результата.
2. Каждый пункт либо выполнен, либо имеет документированное исключение с владельцем и сроком.
3. Отметки и ссылки на доказательства хранятся в тикете или Git-коммите, а не в переписке.
4. Пункты, требующие ручного апрува, помечаются заранее.

## Карта чек-листов

| Чек-лист | Когда применяется | Владелец | Доказательство |
|---|---|---|---|
| Внедрение | запуск автоматизации на площадке | архитектор | решение, inventory, пилотный отчёт |
| Харденинг | изменение security baseline | secops | `--check --diff`, отчёт OpenSCAP |
| Релиз playbook | merge и выпуск роли | автор и ревьюер | PR, CI-лог, CHANGELOG |
| Инцидент | подозрение на компрометацию | SOC | таймлайн, хэши артефактов |
| Air-gapped обновление | перенос контента в изолированный сегмент | sysadmin | акт переноса, хэш-суммы |
| Подключение филиала | новый филиал в управлении | sysadmin | акт приёмки, `ansible-inventory --graph` |
| Изменение VMware | массовая операция с ВМ | виртуальный администратор | снапшот, план отката, лог задач |

## Чек-лист внедрения

Цель — доказать, что автоматизация работает предсказуемо и не зависит от одного инженера.

- [ ] Определены 3–5 сценариев-кандидатов с измеримой частотой выполнения.
- [ ] Выбран baseline: ansible-core 2.17+, Python 3.10–3.12 на control node.
- [ ] Control node размещён в доверенном сегменте, доступ ограничен по сети.
- [ ] Создана сервисная учётка `svc-ansible` с узкими правами sudo.
- [ ] SSH-ключи выпущены через процедуру, приватный ключ хранится с правами `0600`.
- [ ] Inventory описывает филиалы и группы, секреты вынесены из Git.
- [ ] Репозиторий и `requirements.yml` с точными версиями коллекций созданы.
- [ ] CI выполняет `ansible-lint` и `--syntax-check` на каждый merge request.
- [ ] Пилотный playbook прошёл `--check --diff` и применён на одном хосте.
- [ ] Определены окна обслуживания и канал связи с дежурной сменой.
- [ ] Назначены владельцы ролей и порядок эскалации.
- [ ] Зафиксированы метрики: доля автоматизированных задач, время изменений, число откатов.

Результат этапа — пилотный отчёт с перечнем сценариев, временем выполнения и найденными ограничениями. План по этапам согласуется с [дорожной картой](63-roadmap.md).

## Чек-лист харденинга

Харденинг меняет доступ и политики безопасности, поэтому проверки выполняются до применения и после него.

- [ ] Baseline выбран и зафиксирован: CIS L1, DISA STIG или внутренний профиль.
- [ ] Исключения оформлены с владельцем, причиной и датой пересмотра.
- [ ] Роль взята из проверенного источника и закреплена по версии или коммиту.
- [ ] `--check --diff` выполнен на лабораторном хосте той же ОС и версии.
- [ ] Для SSH и sudo используется `validate` (`sshd -t -f %s`, `visudo -cf %s`).
- [ ] Открыта вторая сессия или настроен out-of-band доступ.
- [ ] Раскатка идёт с `serial: 1`, затем долями, с `max_fail_percentage`.
- [ ] Firewall и SSH меняются разными запусками, а не одним play.
- [ ] После применения проверены `sshd -T`, `sudo -l`, `getenforce`.
- [ ] Выполнен повторный скан (OpenSCAP, CIS-CAT) и сохранён отчёт.
- [ ] Дрейф контролируется периодическим `--check` и алертингом.
- [ ] Доказательства приложены к комплаенс-реестру.

Если харденинг затрагивает доступ, таймер отката и вторая сессия обязательны. Маппинг контролей и хранение доказательств описаны в [Комплаенс и доказательства](../security/44-compliance.md).

## Чек-лист релиза playbook

- [ ] Изменение связано с задачей или инцидентом, описана цель.
- [ ] Diff просмотрен вторым инженером, замечания закрыты.
- [ ] Все модули указаны в FQCN, коллекции закреплены в `requirements.yml`.
- [ ] Задачи имеют `name`, рискованные — `changed_when` и `failed_when`.
- [ ] Секреты только через vault или внешний менеджер, `no_log` выставлен.
- [ ] Для конфигов задан `validate`, для сервисов — handler.
- [ ] `ansible-lint` проходит без ошибок, предупреждения разобраны.
- [ ] Molecule или стенд подтвердил идемпотентность повторным прогоном.
- [ ] `--check --diff` выполнен на хосте, близком к боевому.
- [ ] Определены `serial`, `max_fail_percentage` и план отката.
- [ ] CHANGELOG и версия роли обновлены по семантическому версионированию.
- [ ] Релиз подписан, тег запушен, артефакт доступен для повторного запуска.

Релиз без плана отката не выпускается. Процедура ревью и подписи описана в [Ревью и релизы](../quality/52-review-release.md), тестовые требования — в [Тестирование автоматизации](../quality/50-testing.md).

## Чек-лист инцидента

Порядок сохраняет доказательства и не даёт автоматизации уничтожить следы.

- [ ] Инцидент зарегистрирован, назначен координатор и канал связи.
- [ ] Зафиксировано время, затронутые хосты и учётные записи.
- [ ] Автоматические запуски по затронутым группам приостановлены.
- [ ] Собраны логи, конфигурации и список процессов до любых изменений.
- [ ] Для артефактов посчитаны хэши, оформлена цепочка хранения.
- [ ] Изоляция выполнена с предохранителем: не потерян out-of-band доступ.
- [ ] Проверены ключи и токены, которые могли быть на control node.
- [ ] Ротированы скомпрометированные секреты и ключи SSH.
- [ ] Восстановление выполнено из проверенной резервной копии.
- [ ] Проведён повторный харденинг и скан уязвимостей.
- [ ] Составлен таймлайн и разбор причин, назначены действия.
- [ ] Обновлены playbook, детекты и чек-листы по итогам разбора.

Не выполняйте «быстрый откат» через незапланированный playbook на всех хостах: в инциденте это чаще уничтожает артефакты, чем помогает. Полная процедура — в [Реагирование на инциденты](../security/45-incident-response.md).

## Чек-лист air-gapped обновления

- [ ] Определён перечень обновляемых коллекций и пакетов с версиями.
- [ ] Бандл собран в подключённом сегменте из доверенного источника.
- [ ] Для каждого артефакта посчитаны контрольные суммы и подпись.
- [ ] Проверено, что версии совместимы с ansible-core в изолированном сегменте.
- [ ] Носитель проверен на malware в соответствии с регламентом.
- [ ] Перенос оформлен актом с указанием состава и ответственных.
- [ ] Установка выполнена на тестовом хосте, затем на канареечном.
- [ ] `ansible-galaxy collection verify` подтвердил целостность коллекций.
- [ ] Обновлён `requirements.yml` и зафиксирован новый baseline.
- [ ] Предыдущий бандл сохранён для отката.
- [ ] Логи установки и результаты тестов приложены к акту.
- [ ] Запланирована дата следующего обновления.

Регламент переноса и подписи контента — в [Air-gapped среды](../security/48-airgap.md) и [Безопасность цепочки поставок](../secure-dev/15-supply-chain.md).

## Чек-лист подключения филиала

- [ ] Согласованы адресация, DNS-имена и схема доступа через bastion.
- [ ] На хостах создана сервисная учётка и размещён публичный ключ.
- [ ] Проверены версии ОС и Python, для RHEL 8 установлен `python39`.
- [ ] Хосты добавлены в inventory в группу своего филиала.
- [ ] `group_vars` филиала содержат NTP, DNS, прокси и окна обслуживания.
- [ ] `ansible-inventory --graph` показывает ожидаемый состав.
- [ ] `ansible.builtin.ping` и `setup` проходят на всех хостах филиала.
- [ ] Базовый playbook применён с `serial: 1` и проверен на одном хосте.
- [ ] Настроены журналирование и отправка логов в SIEM.
- [ ] Проверено восстановление доступа при обрыве WAN.
- [ ] Филиал включён в расписание периодических прогонов.
- [ ] Подписан акт приёмки, обновлена схема инфраструктуры.

Для филиалов с нестабильным каналом заранее выбирается модель: центральный control node, локальный execution node или `ansible-pull`. Критерии — в [Распределённые филиалы](../admin/20-branch-fleet.md).

## Чек-лист изменения VMware

- [ ] Определены целевые ВМ, кластеры и datastore, проверены лимиты ресурсов.
- [ ] Подтверждено наличие актуальной резервной копии, а не только снапшота.
- [ ] Снапшот создан с осмысленным именем и сроком жизни.
- [ ] Учётная запись API имеет минимальную роль и не является администратором.
- [ ] `validate_certs: true`, сертификат vCenter проверен.
- [ ] Плановая операция проверена на одной тестовой ВМ.
- [ ] Заданы `serial` и пауза между группами ВМ.
- [ ] Для гостевых изменений используется `community.vmware.vmware_guest` с `wait`.
- [ ] Отслеживаются задачи vCenter и события кластера.
- [ ] Снапшот удалён после подтверждения работоспособности.
- [ ] Обновлены CMDB и теги ВМ.
- [ ] Зафиксирован откат: возврат снапшота или восстановление из копии.

Снапшот не является резервной копией: он не защищает от отказа datastore. Требования к бэкапу — в [Резервное копирование и DR](../admin/29-backup-dr.md), операции с ВМ — в [VMware ESXi и vCenter](../admin/24-vmware-esxi.md).

## Проверка результата и хранение доказательств

| Что проверяется | Команда или артефакт | Периодичность |
|---|---|---|
| Соответствие baseline | отчёт OpenSCAP, CIS-CAT | после изменения и ежемесячно |
| Дрейф конфигурации | `ansible-playbook site.yml --check --diff` | еженедельно |
| Полнота inventory | `ansible-inventory --graph` | при каждом изменении |
| Качество кода | `ansible-lint`, результат CI | каждый merge request |
| Доступность хостов | `ansible all -m ansible.builtin.ping` | ежедневно |
| Готовность к откату | наличие предыдущего бандла и тега | перед каждым релизом |

Доказательства хранятся в неизменяемом виде не менее срока, установленного политикой. Для аудита достаточно ссылки на тикет, артефакт CI и отчёт сканера; переписка в чате доказательством не является.

## Безопасность и blast radius

| Риск | Последствие | Мера в чек-листе |
|---|---|---|
| Харденинг без второй сессии | потеря доступа к филиалу | пункт про out-of-band доступ |
| Отметки «на глаз» | ложное чувство готовности | требование доказательства |
| Массовый запуск без `serial` | одновременный отказ хостов | пункты про `serial` и canary |
| Секреты в Git | компрометация всего парка | пункт про vault и `no_log` |
| Изменение без отката | долгое восстановление | пункт про план отката |
| Пропущенный пересмотр исключений | накопление отклонений | дата пересмотра в исключении |

## Комплаенс-маппинг

| Требование | Как закрывается |
|---|---|
| ISO/IEC 27001:2022, A.8.32 (управление изменениями) | чек-листы релиза и VMware-изменения |
| ISO/IEC 27001:2022, A.5.24–A.5.26 (инциденты) | чек-лист инцидента и таймлайн |
| NIST CSF 2.0, ID.IM и PR.PS | внедрение, инвентаризация, управление конфигурацией |
| CIS Controls v8, Control 4 и 7 | харденинг и непрерывное управление уязвимостями |
| Внутренний change management | обязательные доказательства и апрувы |

## Чек-лист

- [ ] Для каждого типа работ выбран соответствующий список.
- [ ] Чек-лист открыт до начала работ, а не заполнен по памяти.
- [ ] Все пункты отмечены или оформлены как исключение.
- [ ] Доказательства приложены и доступны аудитору.
- [ ] План отката проверен, а не только описан.
- [ ] Итоги переданы владельцу процесса и учтены в дорожной карте.
