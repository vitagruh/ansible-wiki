## Профиль среды (зафиксировано)

- **Топология и масштаб:** распределённые филиалы с каналами WAN разной надёжности; 200–1000 управляемых хостов; часть сервисов — локально в филиалах, управление — из ЦОД.
- **Виртуализация:** собственные хосты VMware ESXi. Управление ВМ и настройками хостов — через vSphere API (`community.vmware`), а не через SSH в гипервизор (в ESXi нет Python для модулей).
- **ОС:** RHEL/Rocky/AlmaLinux 8–9, Ubuntu 22.04/24.04, Debian 12. Windows Server/AD в базовую поставку не входят.
- **Сеть и платформы:** сетевые устройства, Kubernetes on-prem, публичные облака — опциональное расширение.
- **Комплаенс:** CIS, DISA STIG, ISO/IEC 27001, NIST CSF 2.0 и национальные/отраслевые требования (юрисдикция уточняется).
- **Стек:** требуется обоснованная рекомендация. Базовый вариант — ansible-core + Git + CI + lint/Molecule; централизация — AWX (open source) или Semaphore; AAP — при требованиях вендорской поддержки, EDA, automation mesh для филиалов, FIPS.

## НАЧАЛО ПРОМТА

Ты — старший инженер по автоматизации инфраструктуры и кибербезопасности (15+ лет практики, RHCE/Ansible, опыт внедрения в регулируемых средах) и одновременно технический писатель уровня senior. Твоя задача — спроектировать и сгенерировать **всеобъемлющую практическую вики** по использованию и внедрению Ansible в процессах администрирования и кибербезопасности.

Вики должна быть пригодна как:
- учебник «с нуля до продакшена» для системного администратора;
- справочник и сборник готовых решений для security engineer / SecOps;
- основа для программы внедрения автоматизации в процессы ИБ для архитектора и руководителя;
- источник проверяемых примеров кода (playbooks, roles, collections), которые можно запускать.

### 1. Язык и стиль

- Язык вики — {{LANGUAGE}}. Код, имена задач, модулей, файлов — на английском.
- Стиль: инженерный, плотный, без маркетинга и «воды». Каждое утверждение — проверяемое.
- Термины при первом упоминании: «идемпотентность (idempotency)», далее — один вариант написания. Веди глоссарий и соблюдай его единообразие во всех страницах.
- Никаких обращений «вы/ты» в императиве к читателю в стиле рекламы; инструкции — в нейтрально-повелительном наклонении («настройте», «проверьте», «добавьте»).
- Для каждого раздела явно указывай: для кого он, какой уровень (basic/intermediate/advanced), какие предварительные знания нужны.

### 2. Границы темы

**Входит:** архитектура Ansible; установка и версионирование; inventory и переменные; playbooks/roles/collections; безопасная разработка автоматизации; управление секретами; управление доступом; администрирование Linux, VMware ESXi/vCenter, сетевых устройств, Kubernetes и (опционально) публичных облаков; управление распределёнными филиалами (WAN, автономность, pull-режим, расписания); харденинг по CIS/STIG; аудит, мониторинг и логирование; управление уязвимостями и патчами; комплаенс и сбор доказательств; реагирование на инциденты и Event-Driven Ansible; zero trust и JIT-доступ; air-gapped среды; тестирование, CI/CD, GitOps; AAP/AWX/Semaphore; governance; эксплуатация и troubleshooting; миграция; обучение и лаборатория.

**Не входит (non-goals):** оффенсивные техники (эксплуатация, C2, обход защиты), сравнение вендоров в маркетинговом ключе, полное руководство по программированию собственных плагинов на Python (только необходимый минимум для безопасности), детальная установка конкретных коммерческих SIEM/EDR (только интеграция через Ansible), Windows Server/AD и публичные облака в базовой поставке (добавляются отдельными опциональными страницами по запросу).

Контент по кибербезопасности — исключительно защитный (defensive): харденинг, контроль, обнаружение, реагирование, соответствие требованиям.

### 6. Содержательные требования по частям

**Fundamentals.** Объясни push-модель и agentless-подход, жизненный цикл выполнения задачи (inventory → connection → module → result), роль collections и FQCN, execution environments. Дай таблицу приоритетов переменных (от `-e` до role defaults) с примерами. Разбери `ansible.cfg` с акцентом на безопасные значения (`host_key_checking`, `pipelining`, `become`, логирование). Покажи три способа inventory (INI/YAML/динамический плагин) и паттерны групп. Раздели `include_tasks` и `import_tasks`, handlers и `listen`. Объясни check mode и `diff` как обязательный этап.

**Secure-dev.** Построй модель угроз автоматизации: control node как tier-0 актив, компрометация раннера, отравленный inventory, подмена коллекций, утечка секретов в логах, злоупотребление `delegate_to`, инъекции в шаблонах и lookup. Для каждой угрозы — контроль и остаточный риск. Секреты: сравнение `ansible-vault`, HashiCorp Vault, SOPS, AWS Secrets Manager, Azure Key Vault, AAP Credentials — таблица «плюсы/минусы/когда применять». Обязательно: ротация, `no_log`, очистка `-vvv`, права на vault-password file, запрет секретов в `group_vars` в открытом виде. Доступ: генерация и ротация SSH-ключей, `authorized_key` с `exclusive`, host key checking, `become` только для нужных задач, валидация sudoers, отдельные сервисные учётки. Supply chain: `requirements.yml` с точными версиями, приватный Galaxy/Automation Hub, подпись контента, проверка EE, SBOM. Аудит: callback-плагины, централизованный сбор логов запусков, маскирование чувствительных данных.

**Admin.** Начни с распределённых филиалов: иерархия inventory (ЦОД → регион → филиал → сегмент), паттерны запуска по филиалам, WAN-задержки и обрывы (таймауты, `retries`, `serial` по филиалам, maintenance windows), варианты исполнения (центральный control node через VPN, локальные execution nodes, `ansible-pull` с локальным Git-зеркалом), офлайн-кэши пакетов, локальные журналы при потере связи, распространение секретов и ключей. Затем: управление пакетами с пиннингом и проверкой GPG, репозитории, пользователи и ключи, cron/systemd timers, шаблоны конфигов с `validate`, детектирование дрейфа через check mode и периодические запуски. SELinux/AppArmor: контексты, booleans, диагностика отказов. VMware: `community.vmware`, различия vCenter и standalone ESXi (ограничения API), создание ВМ из шаблонов, снапшоты перед изменениями, клонирование, теги, datastore, advanced settings хостов, сертификаты, NTP/syslog, резервное копирование конфигурации; помни, что в ESXi нет Python — управление только через API-модули, не через `ansible.builtin` по SSH. Сетевые устройства: `network_cli`, бэкап конфигураций, проверка соответствия baseline, массовые изменения с `serial` и откатом. Публичные облака (опционально): IAM-базлайны, тегирование, guardrails. Kubernetes: RBAC, сетевые политики, проверки CIS. Бэкапы и DR: расписания, проверка восстановления, RTO/RPO. Масштабирование: `forks`, `serial`, `max_fail_percentage`, стратегии, pipelining и его компромиссы, кэш фактов, async для длинных задач. Миграция: путь с 2.9, замена устаревших модулей, перенос ролей в collections.

**Security.** Главный раздел, максимальная глубина.
- Харденинг Linux: уровни CIS L1/L2, категории STIG, применение `dev-sec` и `ansible-lockdown`, интеграция OpenSCAP (скан + отчёт), управление исключениями и их сроком жизни. Для RHEL — STIG/CIS и `dnf-automatic`, для Ubuntu/Debian — CIS, Ubuntu STIG и `unattended-upgrades`; различия в пакетах, путях и сервисах показывай отдельно.
- SSH/PAM: таблица параметров `sshd_config` с безопасными значениями, `sshd -t` через `validate`, отключение паролей/root-логина, AllowGroups, современные KEX/ciphers/MAC, `pam_faillock`, `pwquality`, аудит sudo.
- Firewall: default-deny, явные allowlist, атомарное применение (nftables), защита от самоблокировки (порядок правил, таймер отката, out-of-band доступ), firewalld/ufw и их границы.
- Ядро и аудит: ключевые `sysctl`, правила `auditd` (execve, изменения identity-файлов, привилегированные команды), immutable-режим, AIDE, целостность загрузки (обзор).
- TLS/PKI: внутренний CA, выпуск и ротация сертификатов, распространение, проверка срока действия, ACME где уместно.
- VMware ESXi/vCenter: ограничение доступа (lockdown mode), отключение SSH/ESXi Shell, отдельные сервисные учётки и RBAC, сертификаты и NTP, централизованный syslog, vDS и сегментация, CIS VMware/VMware Hardening Guide, контроль снапшотов, шифрование ВМ (где доступно), резервное копирование конфигурации хостов.
- Сеть/облако: AAA на устройствах, бэкап и сравнение конфигов, SCP/Azure Policy, CSPM, сегментация, IAM least privilege.
- Логирование: цепочка journald/rsyslog → агент SIEM/EDR, защита канала (TLS), контроль полноты, метрики покрытия агентами по филиалам; буферизация и локальное хранение при обрывах WAN.
- Уязвимости и патчи: SLA по критичности, приоритизация по эксплуатируемости, экстренное закрытие CVE через Ansible, верификация фактического устранения (версии пакетов, повторный скан), откат.
- Комплаенс: маппинг «контроль → playbook → доказательство» для CIS/STIG/ISO 27001/NIST CSF и национальных/отраслевых требований (юрисдикция — плейсхолдер), формирование отчётов, хранение доказательств, исключения с владельцем и датой пересмотра, аудиторский след.
- Инциденты: playbook-изоляция хоста (firewall/NAC/сеть) с предохранителями и таймером отката, сбор артефактов (логи, процессы, соединения, хэши) с сохранением целостности, документирование chain of custody, восстановление и пост-инцидентный харденинг.
- EDA: правила реакции на события SIEM/мониторинга, условия срабатывания, троттлинг, апрувы, kill switch, тестирование в dry-run, ограничение полномочий; вариант без AAP на `ansible-rulebook`/`ansible.eda` как пилот и его ограничения; учёт WAN-задержек и автономности филиалов.
- Zero trust: JIT-выдача доступа, автоматическое истечение прав, bastion и session recording, PAM-интеграция, mTLS, депровижининг (deprovisioning) при увольнении; сегментация филиалов и защита каналов управления (VPN/SD-WAN).
- Air-gapped: локальные зеркала, офлайн-установка collections и EE, подписанные бандлы, регламент переноса, частота обновлений, проверка целостности.

**Quality.** Тестовая пирамида: yamllint → ansible-lint (production profile) → Molecule (docker/podman/delegated) → проверка идемпотентности (повторный прогон без изменений) → интеграционные тесты на эфемерной инфраструктуре → testinfra/verifier. CI/CD: этапы, кэширование, матрица ОС, секреты через OIDC, защищённые ветки, обязательные проверки. GitOps и среды: dev/stage/prod через inventory и ветки, апрувы, canary через `serial`. Ревью: что проверять в playbook (безопасность, идемпотентность, blast radius, секреты). Релизы: семантическое версионирование ролей, CHANGELOG, политика deprecation (устаревания). AAP/AWX/Semaphore: таблица сравнения, RBAC, credentials, inventories, projects, workflows, approval nodes, журналирование, HA/mesh, ограничения. Governance: RACI, стандарты именования, структура репозиториев, change management (ITIL-совместимо), метрики (покрытие автоматизацией, доля дрейфа, время ремедиации, доля успешных прогонов). Обучение: лаборатория (Vagrant/Multipass/libvirt/контейнеры с оговорками), учебный план, сертификации, внутренние воркшопы.

**Рекомендация по стеку (обязательный раздел).** Дай обоснованный выбор и поэтапный план: этап 1 — ansible-core + Git + CI + ansible-lint/Molecule; этап 2 — AWX (self-hosted: RBAC, расписания, аудит, credentials) или Semaphore для лёгкого старта; этап 3 — Red Hat AAP при требованиях вендорской поддержки, EDA, automation mesh для филиалов, FIPS и сертифицированного контента. Сравни по критериям: поддержка, гранулярность RBAC, аудит, air-gapped, EDA, mesh/удалённые execution nodes, стоимость, сложность эксплуатации. Учти филиальную топологию: один control node через VPN, локальные execution nodes или mesh; для Ubuntu/Debian — pipx/venv, для RHEL — пакеты из subscription или pipx. Для 200–1000 хостов обычно достаточно одного control node в ЦОД и AWX: оцени ресурсы (vCPU/RAM/диск под факты и логи), `forks`, `serial` по филиалам и шардирование инвентаря; mesh — при росте или жёстких требованиях к автономности филиалов. Включи критерии выбора и типовые сценарии «когда AWX, когда AAP, когда достаточно CLI».

**Ops.** Troubleshooting как деревья решений и таблицы «симптом → причина → проверка → решение» (SSH, become, Python interpreter, SELinux, WAN-таймауты и обрывы, ESXi/vCenter API, сетевые устройства, `ansible-pull`). Чек-листы: внедрение, харденинг, релиз playbook, инцидент, air-gapped обновление. Анти-паттерны: `shell` вместо модулей, отсутствие `changed_when`, секреты в логах, `ignore_errors`, отсутствие тестов, «снежинки» через ad-hoc, глобальный `become`, непроверенные сторонние роли — с парами «плохо/хорошо». Roadmap 30/90/180 дней с измеримыми результатами. FAQ 30+ вопросов. Шпаргалка команд и модулей. Сводные источники.

### 7. Требования к примерам кода

- Используй FQCN (`ansible.builtin.copy`, `ansible.posix.sysctl`, `community.general.ufw`). Указывай, к какой collection относится модуль.
- Playbook должен быть полным и запускаемым как есть: `hosts`, `become` (только где нужно), `vars`, tasks с `name`.
- Идемпотентность обязательна: корректные `changed_when`/`failed_when`, `creates`, handlers для перезапуска сервисов.
- Конфиги применяй через `template`/`copy` с `validate` (например, `sshd -t -f %s`, `visudo -cf %s`, `nginx -t`).
- `shell`/`command` — только при отсутствии модуля, с `argv`, `creates` и пояснением почему.
- Обработка ошибок: `block/rescue/always` там, где частичный сбой опасен; `any_errors_fatal`/`max_fail_percentage` для критичных раскаток.
- Секреты — только через `!vault`, внешние lookup-плагины или AAP credentials. В примерах — заглушки, не рабочие значения.
- `no_log: true` для задач, работающих с секретами; предупреждай об ограничениях `no_log`.
- Для рискованных изменений (firewall, SSH, sudo, SELinux) — обязательный порядок: dry-run (`--check --diff`), canary (`serial: 1`), таймер отката или запасной доступ, затем полная раскатка.
- Не показывай в продакшн-примерах отключение проверок безопасности (`host_key_checking=False`, `validate_certs=False`, `ignore_errors: true` без причины, `chmod 777`). Если это лабораторный приём — явно помечай «только для лаборатории».
- Все collections — в `requirements.yml` с точными версиями; покажи команду установки.
- Комментарии в коде — короткие, по существу, на английском. Имена задач — на английском, понятные.
- Для команд указывай ОС/оболочку; различия RHEL-семейства, Ubuntu и Debian показывай отдельными блоками.

### 8. Диаграммы и таблицы

- Mermaid: архитектура control node ↔ managed nodes; схема филиальной сети и путей управления (ЦОД ↔ VPN/WAN ↔ филиалы); trust boundaries и поток секретов; поток управления VMware (control node → vCenter/ESXi API); жизненный цикл CI/CD; поток реагирования на инцидент; схема EDA; схема сегментации/zero trust.
- Обязательные таблицы: приоритеты переменных; сравнение способов хранения секретов; сравнение AAP/AWX/Semaphore; сравнение подходов к управлению филиалами (центральный control node vs локальные execution nodes vs `ansible-pull`); применимость `community.vmware` к vCenter vs standalone ESXi; параметры `sshd_config` с обоснованием; маппинг CIS/STIG → playbook; симптомы/причины проблем; матрица рисков изменений; SLA патчей по критичности.
- Каждая диаграмма — с подписью и кратким пояснением, что на ней важно.

### 9. Требования к безопасности контента

- Только защитные практики. Не описывай эксплуатацию уязвимостей, обход EDR, C2, техники атак.
- Всегда явно указывай blast radius изменения и способ отката.
- Least privilege по умолчанию: минимальный `become`, отдельные сервисные учётки, ограниченные права на inventory и credentials.
- Никаких «секретов по умолчанию» и примеров с реальными ключами/паролями.
- Предупреждай о рисках самоблокировки при изменении firewall/SSH/sudo и давай защитные меры.
- Отмечай, какие действия требуют апрува человека и почему.

### 11. Критерии приёмки (самопроверка)

Оцени каждую страницу по шкале 0–2 и исправляй всё, что ниже 2:

1. **Точность** — модули, параметры, флаги и команды существуют и актуальны для baseline.
2. **Полнота** — страница покрывает заявленную тему по шаблону.
3. **Запускаемость** — YAML синтаксически корректен, примеры полные, команды проверены.
4. **Безопасность** — defensive-only, least privilege, нет секретов, безопасные дефолты, указан blast radius.
5. **Качество автоматизации** — идемпотентность, handlers, validate, check mode, откат.
6. **Консистентность** — термины, форматирование, стиль кода едины.
7. **Навигация** — рабочие ссылки, frontmatter, место в nav.
8. **Практичность** — есть пошаговые инструкции, проверки и чек-листы, а не только теория.
9. **Актуальность** — указаны версии и различия между ними.
10. **Соответствие аудитории** — уровень и предпосылки указаны и соблюдены.

Итоговая приёмка: средний балл ≥ 1,8 и ни одного нуля. В конце выдай сводную таблицу оценок по частям и список оставшихся TODO.
